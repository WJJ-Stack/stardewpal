## 项目描述（简历正文）

**StardewPal · 星露谷物语多模态 RAG 问答系统**（个人项目）

技术栈：Python / FastAPI / SQLite(FTS5 + sqlite-vec) / ONNX Runtime / 多模态 LLM / Docker

- **数据管道**：从 BWiki 抓取 5,259 个页面，自行实现 MediaWiki 语法清洗
  （模板转写、表格展平、infobox 合并、链接归一），产出 2,086 篇有效文档、
  7,834 个文本块、520 个结构化物品实体；中文物品名映射 1,119 条。
- **混合检索**：BM25 + 向量双路召回，RRF 融合；针对中文查询的
  疑问词干扰问题，实现「整句 + 实体」双查询融合与实词覆盖率降权。
  **Hit@1 51.9% → 89.7%，MRR 0.691 → 0.946**（消融实测）。
- **多模态链路**：截图直接送入 VLM，仅提取画面文字作为检索线索，
  场景判断交由检索结果决定；避免「先判断场景再检索」的自我强化错误。
- **确定性计算**：物品品质倍率、加工收益、多选题中位数等数值题
  全部走代码计算并保留推导步骤，不让模型心算。
- **工程化**：122 个单元测试 + 4 组回归测试；ruff 零告警；
  单镜像部署（含 LFS 指针自愈、索引启动自检）。

## 面试可展开的技术点

### 1. 为什么不能只做向量检索
向量单路 Hit@1 66.3%，看似不错，但漏掉精确数值。
玩家问「金星蓝莓卖多少」，向量把语义相近的《蓝莓千层酥》排前面；
BM25 能抓住「金星」「卖价」这类关键词，但处理不了同义表达。
必须双路。

### 2. 中文 BM25 的一个隐蔽坑
SQLite FTS5 没有中文分词器，只能把句子切成双字前缀：
```
"沙漠节什么时候办" → "沙漠"* OR "漠节"* OR "节什"* OR "什么"* OR "么时"* OR "时候"*
```
「什么」「时候」在语料里到处都是，OR 一放就主导了排序，
正确答案《沙漠节》连前 10 都进不去。

但如果直接把查询压成实体「沙漠节」，另一种查询又会坏：
「你一共走了多少步」压成「你一/共走/多少」后，会被短文档反超。

**解法是两路都查、RRF 融合**，让两种策略互补而不是互相打架。

### 3. 小片段检索给到大窗口（small-to-big）
切块按 480 字窗口，把「问题」和「答案」切开了：
```
ord 0   「每年春季 15、16、17 日」        ← 日期在这
ord 18  「三个数字的中间值将是正确答案」   ← 规则在这
ord 19  「你一共走了多少步？」            ← 命中 BM25 第 1
```
只给 rank1 等于给模型一道没有答案的题，它只能编。

解法：命中块作为锚点，拼接同章节相邻块。**两个约束都是踩出来的**：
- 只在同一章节内扩展（否则商铺表格会被拼进服装说明，模型会把 A 的结论套到 B）
- 条目首段按相关性决定是否附带（否则「三花蛋节日后消失」会被套到服装上）

### 4. 不该让模型做的事
- **心算**：中位数题模型两次里错一次（把「中间值」当平均值，算出选项里没有的数）
  → 改成确定性工具，3/3 稳定
- **判断要不要检索**：同一问题问两次，一次查一次不查
- **判断资料是否充分**：曾把含答案的《沙漠节》判为「不充分」
- **判断检索结果相关性**：曾把沙漠节相关页面全判为不相关

这些中间层全部删掉了，代码净减 819 行。

### 5. 最值得讲的复盘：标准答案和被测系统共享同一个错误
工具算 `防风草→腌菜 = 35 × 2 = 70`，
wiki 原文是 `蔬菜基础价格 × 2 + 50`，正确应为 120。

**但评测集也用这个错误公式生成，所以「artisan 100%」是假象。**
自洽闭环，永远测不出错。

最终是靠前端截图里引用原文明晃晃写着「×2+50」，和旁边的 70 摆在一起才发现的。

教训：数值类 RAG 的最大风险不是模型幻觉，是事实源本身有错。
